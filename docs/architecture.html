mhi2-aid-carplay architecture

What the system does in a Passat B8 (Discover Pro MHI2 MU1161, AID 791):
  • where it gets the picture and the data from the phone;
  • which head unit files it replaces;
  • where it hooks into factory code;
  • what it never touches.
CarPlay (paths A-C) is shown as in release v1.4.1 "rg-main" (the optional speed-limit package sl is not drawn). Android Auto (path D) is work in progress: it is not in any release and is shown as tested in the car on 2026-11-04.

Lines:
  • blue: the map picture;
  • orange: guidance data;
  • purple dashed: code hooked into the HMI;
  • green: factory channels (BAP, keys, map gate).
We change nothing on the MOST bus: our data travels in factory channels.

A · CarPlay map picture on the AID

iPhonesecond H.264 stream 800×480→ dio_manager = wrapper.shfactory file moved to stock_first/dio_manager.real→ core.so in the dio_manager processLD_PRELOAD; asks the phone for the cluster stream→ ring in /ramdisk→ altscreen-most-bridgetakes the MOST video channel (context 72)→ AID 791
  • What we overwrite: only the dio_manager file (the factory CarPlay/AirPlay receiver). In its place is a script that starts the real factory program with core.so (LD_PRELOAD) and the security-bridge library added.
  • What core.so intercepts: the CarPlay session in dio_manager. It offers the iPhone a second "instrumentcluster" screen with:
    • the map URL;
    • the safe area;
    • the frame rate (40 in map-square-fps40);
    • the physical size of 240×144 mm.
    It writes the finished H.264 frames into the ring. It also listens on UDP 127.0.0.1:7032 to change the zoom when the zoom package asks.
  • A variant is one file: switching the map layout (map-clean, map-square…) replaces only core.so, then a restart. All variants are built from one omonob base (pinned by hash) with the patches in patches/mu1161/build_core.py.
  • The factory gate stays: the AID shows the stream only when the factory HMI (mostkombi, WaitForServices) decides the VW navigation is ready, about 43 s after start. The fast start audit covers the attempts to get past that gate. They failed, and the topic is closed.

B · Native VW route guidance from the iPhone (arrows, ETA, lanes)

iPhoneiAP2 RouteGuidance 0x5201…, lanes 0x5204→ ipod-drvr-iap2.so + iap2.cfgreplaced: tomasz-twardzicki's patch chain + our log gate→ rgi-observer pmcp-r1reads /dev/ipod0/rgi-events→ /ramdisk/carplay-route-guidance→ rg (Java)LiveBridge in the NavSD classes→ BAP NavSD → AID
  • iAP2 driver: the factory iPod/iAP2 driver gets 6 hooks and 3,271 B of added code, and iap2.cfg gets a new [ident] block. With that, the head unit tells the iPhone "I support RouteGuidance" and the phone starts sending maneuvers. Factory copies go to carplaymaps/rollback/. This is the only place we write to /mnt/system (it goes back to read-only after the write). Our 76-byte log gate (v1.4) lets Tomasz's per-byte receive log run only while /dev/shmem/pmcp-rgi-debug exists; it is off by default.
  • Reader: rgi-observer starts from the pmcp block in lsd.sh when the SYSTEM_ON marker exists, and writes the guidance state to a file in RAM. Since v1.4 it is pmcp-r1, derived from Tomasz's reader:
    • a supervisor process and a worker that does the driver reads;
    • after 1 s without data the supervisor writes one "invalid" record, so no stale arrow stays on screen;
    • after 10 s it kills the stuck worker and starts a new one with a growing delay;
    • it never ends by itself, and a file lock keeps a second reader out.
    The earlier reader ended for good after 1.5 s without data, and the arrows were gone until the next start.
  • In the HMI: the rg package changes where the factory navigation classes (NavSD, LaneGuidance, TurnToInfo) get their data: from that file instead of from the VW navigation. Every call is guarded: on an error the factory code runs. It carries:
    • arrow, distance, ETA (Tomasz's MU1427 port, with his strict iPhone → VW maneuver mapping);
    • lanes (Tomasz's MU1367 v1.4.0), with the VW U-turn symbols 114 (left) and 146 (right), which went back to tomasz-twardzicki as PR #8;
    • the distance bar before the maneuver, the current street name and feed recovery (Tomasz's MU1367 v1.4.3);
    • maneuver fallbacks where the strict mapping gives no arrow: the start of a route, roundabout turns, U-turns and ramps without an angle (table after harman-f's MibrRgiManeuvers).
  • The AID draws the arrow, distance, ETA and lanes with its own factory widgets. It gets nothing new, only different data in a known BAP format.

C · HMI: one block in lsd.sh and the Java packages

The head unit HMI is the factory J9 Java VM running lsd.jxe. We do not change that file. The factory start script lsd.sh gets one block before J9 starts: it reads HMI_BOOT and puts our JARs before the factory classes (-Xbootclasspath/p:). Each JAR holds factory MU1161 classes changed only in selected instructions (ASM, with a check of the pattern and the hit count).

PackageWhere it hooks in (factory class)What it changes
naiCarPlayModeHandling, DSICarplayProxy.requestModeChange, ASLNavigationServices.stopGuidance, AA NavigationListener While the iPhone navigates, the head unit does not stop the VW navigation and does not take guidance away from the phone. Without it the AID map goes off when the phone navigates.
npHsmTarget.initializeDSI, CurrentStationInfo An extra listener for the NowPlaying attribute (not read by the factory code). The AID shows title, artist and album instead of "Apple CarPlay".
rgNavSD classes + LaneGuidance + TurnToInfo Guidance data, lanes, distance bar and street name from the iPhone instead of from the VW navigation (path B). Replaces rg/rglu of v1.3 (java-update).
zoomDSIKeyPanelDispatcher.updateKey2 A short press of the up/down arrow on the steering wheel sends zoom-in/zoom-out over UDP to core.so. The key is not taken over: the cluster menu still works.
dnASLHandler (after startService and on entry to handleDayNightMode) Sends the day/night mode to the phone again after 5, 15 and 30 s, because the cluster screen appears later than the single factory send.

Trial start: a new JAR set loads once. It stays only after "5. Confirm" in GEM during that start. Without a confirm the next start is factory, so a broken set is gone after one restart.

D · Android Auto (work in progress, not in a release)

The picture takes the same path as CarPlay: the same RAM ring, the same altscreen-most-bridge and the same MOST channel. Two things differ:

  • the input: the AA receiver gal instead of dio_manager;
  • who takes the MOST channel: the feeder instead of the CarPlay supervisor.

The two phones do not work at the same time.

Android phonesecond "cluster" screen, H.264→ gal = wrapper.shfactory AA receiver kept as gal.real→ libgal_hook.soLD_PRELOAD; offers the second screen→ aa-most-feedertakes MOST, writes into the ring→ altscreen-most-bridge→ AID 791
  • What we overwrite: the file /mnt/app/eso/bin/apps/gal (the factory Android Auto receiver). In its place is a script that starts the factory program (gal.real, checked by hash) with the hook added. smartphone_integrator.json and /mnt/system stay factory. MacsInSpace edits that file; we do not.
  • What the hook intercepts: the AA session in gal. It offers the phone a second 800×480 screen (the cluster) and hands its H.264 stream to a "player", which is our feeder. Base: MacsInSpace mib-cluster-map @ 07361db, plus our patches:
    • nothing is read from the SD card;
    • a fresh IDR frame on request;
    • translation of the 1.7 navigation messages to the 1.2 ones the head unit's receiver understands.
  • Who takes the MOST channel: with CarPlay the supervisor does it; with AA the feeder does it itself (dmdt, context 72). After the session the feeder gives the channel back to the VW map. It leaves the channel alone while CarPlay holds it (/ramdisk/carplay-bridge.ready plus a running bridge process) and waits for that up to 20 s. After the takeover it waits 5 s and then holds and repeats the phone's first key frame (IDR) for 3 s. Since feeder v8 it reuses CarPlay's 16 MB ring in place: dio_manager keeps that ring mapped, so deleting it filled /ramdisk and AA had no picture after CarPlay.
  • Gamma (maneuvers as native VW arrows): the hook reads the Google Maps navigation messages before the translation overwrites them:
    • 0x8003: status;
    • 0x8006: next maneuver;
    • 0x8007: metres to that maneuver.
    It writes them in tomasz-twardzicki's mailbox format (synthetic iAP2 0x5201/0x5202) to its own directory /ramdisk/pmcp-aa-rg, never to the CarPlay directory. The guidance package rg (since v1.5.0) reads that directory on an AA connection and works like rg with CarPlay. Distance and time to destination stay factory, because the AA picture shows them. Stale data expires after 1.5 s. In a test drive 94 of 94 maneuvers were recognised.
  • AA trial start: separate from the Java one. AA_BOOT is the set id: the mode plus hashes of the hook, the feeder and the settings. A new set runs with the hook for one head unit start only, and stays after "5. Confirm" (or "AA Confirm"). The markers DISABLED (rescue card) and AA_DISABLED turn the hook off. "AA remove" and "8. Remove everything" put the factory gal back, only on a pmcp install and only from a gal.real with the factory hash. Android Auto is installed with main-screen button "3. Install Android Auto" (it replaces an AA set the card does not support, the same way); its details are on the screen aa_advanced. Button 4 never changes Android Auto.
  • Known limits:
    • open: in about half of the connections the picture starts dark with artefacts, and it can also be lost during a drive, because the phone sends one key frame per session; the workaround is to plug the phone in again;
    • re-sending the video config to the phone drops the connection about 9 s later, so it is not used;
    • the CarPlay supervisor does not know about AA, so plugging in an iPhone during AA takes the channel;
    • AA needs path A, because it uses that path's bridge;
    • we do not install VCAndroidAuto.jar (adi961): on a VW it blanks the cluster map once a route starts.

Installer and rescue paths

Card 1: pmcp.sh from the GEM menu (M.I.B.)

STOCK→ 2. Install CarPlay → VIDEOstage A: dio_manager, carplaymaps→ 4. Install additional features → JAVA (trial)→ 5. Confirm → JAVA
  • It first checks every head unit file and card file by exact hash and size. An unknown state (UNKNOWN, e.g. another mod) means no changes.
  • It copies to a staging directory, checks the copies, and only then switches with one mv. After the switch it checks again; on an error it rolls back automatically.
  • The factory copies of lsd.sh, dio_manager, the iAP2 driver and iap2.cfg are kept in /mnt/app/carplaymaps/rollback. "8. Remove everything" restores all of them and checks the hashes.
  • Updates in place (since v1.4; now button 4, earlier button 3): it first replaces an earlier card's driver and reader (rg-update, known hashes only) and its Java packages (java-update: one new set, one trial start). New JARs get file names no earlier card used, so a confirmed set never runs an unconfirmed file. Route guidance or Java files the card does not support (e.g. a set with an unknown package, or after the rescue card) are first put back to the verified factory copies (features-reset).
  • On the Mac, tests run pmcp.sh on a copy of the head unit file tree (ksh and mksh) and simulate a power loss before every write.

Card 2: rescue

  • It starts by itself in update mode (SWDL), without GEM. In that mode the pmcp block in lsd.sh does nothing, so the HMI is always factory.
  • It restores the factory HMI and writes /mnt/persist/pmcp/DISABLED, which turns the whole Java block off. It also puts the factory iAP2 driver back (both driver sizes, v1.0-v1.3 and v1.4). Its log is PMCP_RESCUE_LOG.txt (RESULT=OK).
  • Stage A (picture) does not touch the HMI. The worst result of a failure there is no CarPlay; GEM and "8. Remove everything" still work.

State outside the head unit

  • The AID is a separate ECU. A head unit restart does not reset it. After the kf4 attempt only letting the car sleep helped (locked, 15-20 min).

Rules:
  • no cross-flash;
  • a fail-closed installer: hash and size, staging, rollback, rescue card;
  • no map sequence is sent to the AID before the VW navigation is really ready, and the HMI start order is not changed (lessons from the kf4 audit).
